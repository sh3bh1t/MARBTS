\begin{abstract}
MARBTS is a sandboxed Red/Blue cyber-defense simulator for studying autonomous attacker-defender interaction without touching live systems or invoking real exploit tooling. The project models a network as a synthetic graph whose nodes carry services, vulnerability markers, security levels, compromise states, detection states, and isolation flags. Red and Blue agents interact with that graph through a fixed safe action vocabulary: Red can scan, exploit, move laterally, or escalate; Blue can monitor, patch, block, or isolate.

This paper refines the MARBTS design and reports repository-verified results from the current implementation. The system provides scenario validation, NetworkX-based graph construction, legal-action generation, deterministic rule-based policies, bounded adaptive planning policies, seeded simulation, policy rationales, structured timestep logs, metric artifacts, comparative reports, and notebook-oriented analysis assets. Results from the checked-in experiment reports show deterministic replay for the rule baseline and measurable behavioral differences when the adaptive Red planner is introduced. The contribution is a lightweight, inspectable, and reproducible research testbed for policy-level cyber-defense experimentation under explicit safety constraints.
\end{abstract}

Autonomous cyber defense, Red team simulation, Blue team simulation, multi-agent systems, graph-based network modeling, explainable agents, cyber range, reproducible experimentation.

\section{Introduction}
Cyber-defense research needs environments where offensive and defensive strategies can be repeated, inspected, and compared under the same initial conditions. Live cyber ranges can provide realism, but they are expensive to operate, difficult to reset exactly, and unsuitable for early-stage policy experiments that should not involve real exploit chains. MARBTS addresses this problem as a local, fully abstract simulator: it studies policy behavior on a synthetic graph rather than on operational infrastructure.

The simulator is intentionally not an exploitation framework. Red actions mutate symbolic state only when the transition engine permits it, and Blue actions similarly update graph attributes or connectivity. For example, an exploit action can move a node from \texttt{none} to \texttt{user} compromise, a patch action can increase a security level and remove vulnerability exposure, and a block action can remove an edge. By keeping the environment abstract, MARBTS preserves a useful attacker-defender interaction loop while avoiding unsafe operational behavior.

The project also emphasizes research usability. Each run is associated with a scenario identifier, seed, horizon, run metadata, timestep records, state-diff payloads, policy rationale payloads, and metric summaries. These artifacts make it possible to inspect not only the final compromise count but also the sequence of Red and Blue choices that produced it. The current repository includes command-line entry points, experiment presets, notebooks, Docker Compose profiles, generated reports, and figures that support reproducible analysis.

\section{Related Work}
MARBTS is positioned between adversary emulation systems and learning-oriented cyber simulation environments. MITRE ATT\&CK provides a shared vocabulary for adversary tactics and techniques \cite{attack}. CALDERA operationalizes adversary emulation and automated response workflows around ATT\&CK concepts \cite{caldera}, and Miller et al. discuss planning-based adversary emulation when the environment contains unknowns \cite{miller}. MARBTS draws from this planning-oriented perspective, but keeps execution at the graph-state level rather than launching agents, command-and-control infrastructure, or real procedures.

CyberBattleSim and CybORG are closer to MARBTS in their use of abstract cyber environments for autonomous-agent research. Microsoft CyberBattleSim describes simulated enterprise networks using high-level computer-network and cybersecurity abstractions for reinforcement-learning experiments \cite{cyberbattle}. CybORG similarly frames autonomous cyber operations as a gym-style environment for Red and Blue decision-making research \cite{cyborg}. MARBTS differs in emphasis: the present repository prioritizes deterministic baselines, explainable heuristic/adaptive decisions, structured artifact generation, and lightweight local repeatability over trained reinforcement-learning agents.

The implementation also relies on standard scientific Python infrastructure. NetworkX is used to represent the mutable graph state \cite{networkx}, Matplotlib is used by the reporting layer to render figures \cite{matplotlib}, pytest supports validation, and Docker Compose assets package repeatable command profiles \cite{pytest}, \cite{compose}.

\section{Objectives}
The implementation goals verified from the repository are:

\begin{itemize}
    \item Represent synthetic networks as validated JSON scenarios with typed nodes, edges, services, vulnerabilities, and security attributes.
    \item Build a NetworkX graph from validated scenarios and use it as the source of truth for legal actions, transitions, metrics, and reports.
    \item Provide a constrained action vocabulary for Red and Blue agents so that all behavior remains abstract and sandboxed.
    \item Support deterministic rule-based policies and bounded adaptive-planning policies for both actors.
    \item Attach rationale summaries, score breakdowns, predicted effects, planning traces, and policy metric snapshots to decisions when policy objects are used.
    \item Execute seeded experiments and produce reproducible run artifacts, aggregate reports, comparison reports, and figures.
    \item Expose researcher workflows through Python scripts, packaged CLI commands, notebooks, Docker Compose profiles, and release-readiness validation assets.
\end{itemize}

\section{Methodology}
MARBTS separates scenario validation, graph construction, legal-action generation, policy selection, state transition, logging, and reporting. This separation reduces coupling between experimental setup and policy logic, and it makes individual components replaceable.

Fig.~\ref{fig:marbts_architecture} summarizes the repository-verified architecture. Scenario and runtime inputs are validated before graph construction. The action surface is generated from the current graph state. Policy objects choose among legal actions. The simulation kernel applies state transitions and records artifacts for post-run analysis.

\subsection{Scenario Validation and Graph Construction}
Scenario files are JSON documents containing metadata, nodes, and edges. The validator in \path{src/schemas/scenario.py} requires each node to define \texttt{node\_id}, \texttt{node\_type}, \texttt{services}, \texttt{vulnerabilities}, \texttt{security\_level}, \texttt{compromised\_state}, \texttt{detection\_state}, and \texttt{isolation\_state}. Node types currently include server, database, IoT, and endpoint. Compromise states are \texttt{none}, \texttt{user}, and \texttt{privileged}; detection states are \texttt{undetected}, \texttt{suspected}, and \texttt{confirmed}.

After validation, \path{src/environment/graph_builder.py} creates a \texttt{networkx.Graph} and attaches node attributes as mutable graph data. The graph is then used by the legal-action generator, transition engine, simulation kernel, and metrics layer. This design gives all components a consistent state representation.

\subsection{Legal Actions and Transition Semantics}
The current action vocabulary is defined in \path{src/hart/enums/agent_enums.py}. Red actions are \texttt{scan}, \texttt{exploit}, \texttt{lateral\_move}, and \texttt{escalate}. Blue actions are \texttt{monitor}, \texttt{patch}, \texttt{block}, and \texttt{isolate}. The generator in \path{src/environment/legal_actions.py} emits only actions compatible with the current graph. For example, isolated nodes are skipped for Red actions, lateral movement requires an already compromised source node, and Blue block actions are created from existing edges.

The transition engine in \path{src/environment/transitions.py} implements the state-changing parts of this vocabulary. Exploit-like Red actions advance compromise one level when allowed. Patch raises security level by one up to a maximum, removes one vulnerability when present, and can reduce compromise by one level. Isolate sets a node's isolation flag and removes its connected edges. Block removes a selected graph edge. Scan and monitor are informational no-op actions in the current kernel, which is important when interpreting baseline results.

\subsection{Policy Layer}
The rule-based policies in \path{src/agents/red/rule_based.py} and \path{src/agents/blue/rule_based.py} use deterministic heuristic scores and stable tie-breaking. This makes them useful for regression and reproducibility testing because the same scenario, seed, and horizon should produce the same action sequence.

The adaptive policy in \path{src/agents/adaptive/planning.py} uses bounded planning over candidate actions. It computes base utility, projected compromise deltas, discounted horizon utility, target affinity from node security level, optional exploration terms, optional reduced-observability behavior, and optional deception hooks. The current model-routing path is heuristic by default; remote routing fields exist in configuration models, but the checked-in implementation does not require an external LLM or cloud service.

\subsection{Seeded Simulation Workflow}
The simulation kernel in \path{src/simulation/kernel.py} coordinates a turn-based loop. At each timestep it captures a pre-state reference, generates Red legal actions, obtains a Red decision, applies the Red transition, generates Blue legal actions from the resulting graph, obtains a Blue decision, applies the Blue transition, computes a post-state diff, and records metrics. Fig.~\ref{fig:marbts_workflow} shows this workflow.

\subsection{Artifacts and Interfaces}
Run artifacts include \path{run_metadata.json}, \path{timesteps.jsonl}, and \path{policy_metrics.json}. Aggregate experiment scripts produce reports under \path{artifacts/reports/}, metrics under \path{artifacts/metrics/}, and figures under \path{artifacts/figures/}. The repository includes scripts and packaged CLI commands for multi-seed reports, policy matrices, stress suites, ablation packages, comparative reports, container profiles, and release validation. Notebook workflows provide replay, comparative, policy-matrix, and ablation walkthroughs.

\section{Implementation}
\subsection{Package Structure}
The codebase is organized around clear package boundaries. The \path{src/hart/} layer stores shared enums and dataclass contracts. The \path{src/schemas/} package validates scenarios. The \path{src/environment/} package builds graphs, generates legal actions, and applies transitions. The \path{src/agents/} package implements Red, Blue, and adaptive policies. The \path{src/simulation/} package runs the turn loop and writes state diffs. Observability, metrics, experiments, visualization, CLI, and utility modules are isolated in their own packages.

\subsection{Observability and Reproducibility}
The logging path records both actions and outcomes. A timestep entry contains Red and Blue action intents, rationale payloads, change flags, transition reasons, post-state diffs, compromised-node deltas, and policy metric snapshots when available. Sequence hashes allow repeated runs to be compared for deterministic consistency. The multi-seed and policy-matrix reports aggregate these hashes into deterministic consistency ratios.

\subsection{Experiment Tooling}
The repository contains presets for the multi-seed baseline, policy experiment matrix, stress-test suite, and ablation package. The same workflows are exposed through scripts such as \path{scripts/run_multi_seed_report.py} and packaged commands such as \texttt{marbts-multi-seed-report}. Docker Compose profiles invoke the canonical experiment commands inside a project container image. Notebook walkthroughs can either analyze existing artifacts or regenerate canonical inputs when configured to do so.

\subsection{Stress-Test Suite}
The stress-test report contains two profile groups: \texttt{scale\_scenarios}, which runs the rule baseline, containment-stress, and scale-chain-6 scenarios without ablations, and \texttt{noise\_observability\_constraints}, which runs containment-stress and scale-chain-6 with observability/noise proxy conditions. These values should be read as workflow validation over the current small scenario set rather than as a general security benchmark.

\section{Discussion}
The repository-verified results show that MARBTS can generate reproducible baselines and distinguish policy behavior under controlled conditions. The most important observation is not that one policy is universally better than another, but that the artifact pipeline makes the difference inspectable. The adaptive Red run leaves behind changed action records, state diffs, containment actions, and comparative figures; the rule baseline leaves behind a stable no-op scan/monitor sequence. This traceability is valuable for teaching, debugging, and incremental research.

The results also reveal current limitations. Scan and monitor do not yet mutate detection or knowledge state. The adaptive layer is a bounded heuristic planner rather than a trained reinforcement-learning or LLM-driven agent. Remote model-routing configuration exists, but the checked-in path falls back to heuristic behavior unless extended. The baseline scenario is intentionally small, so the reported numbers should not be interpreted as operational security performance.

\section{Contributions}
This work contributes:

\begin{itemize}
    \item A sandboxed Red/Blue simulation environment that models cyber behavior as abstract graph-state transitions.
    \item A validated scenario pipeline and NetworkX graph state used consistently by actions, transitions, metrics, and reports.
    \item Deterministic rule-based policies and bounded adaptive-planning policies for both Red and Blue actors.
    \item Explainable decision records with rationales, score components, planning traces, predicted effects, and policy metric snapshots.
    \item Seeded experiment tooling for multi-seed baselines, policy matrices, stress suites, ablations, comparative reports, notebooks, and container profiles.
    \item Repository-backed figures and artifacts that support reproducible paper claims.
\end{itemize}

\section{Conclusion}
MARBTS demonstrates that a lightweight cyber-defense simulator can support safe, repeatable, and explainable policy experimentation without relying on live infrastructure or real exploit execution. The current implementation validates scenario inputs, constructs graph-based environments, generates legal actions from state, applies controlled transitions, and emits structured artifacts for replay and comparison.

The checked-in experiment reports confirm deterministic baseline replay and show that the adaptive Red planner changes compromise and containment outcomes in the canonical policy matrix. These results are intentionally narrow, but they validate the research workflow: policy changes can be run, compared, visualized, and audited through local artifacts.

\section{Future Work}
Future development should focus on richer state semantics and stronger evaluation. Useful extensions include mutating scan/monitor knowledge state, improving detection dynamics, expanding scenario libraries, adding partial observability, strengthening deception and noise models, introducing trained RL agents, integrating optional model-backed planners safely, and building dashboards for replay and trajectory comparison. Larger benchmark suites would also help separate scenario-specific behavior from policy-level effects.
